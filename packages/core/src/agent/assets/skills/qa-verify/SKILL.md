# 真机与网页验证

用 openLoop 的 QA 引擎执行验证：先确认设备，再用自然语言步骤驱动界面，最后读回截图下结论。

## 流程

1. **明确验证点**：从用户需求或本次改动里提炼 3 到 8 个可观察的预期结果。每个预期结果都要能在一屏里看出真假。
2. **选设备**：调用 `qa_device_status`。优先选空闲设备；目标设备显示「占用中」时如实告知用户排队原因，不要强行操作。
3. **组织用例**：按「操作 → 断言」交替排列。断言写成屏幕上的可见事实，例如「页面显示登录成功」而不是「登录逻辑正确」。
4. **执行**：调用 `qa_run_suite`，一次传入完整步骤列表。工具会返回结论、失败原因与每步截图的相对路径。
5. **读证据**：失败时读取截图确认是产品缺陷还是用例写错。截图路径可直接用 read 工具打开。
6. **汇报**：给出通过/未通过结论、失败的具体步骤与截图路径。用户没有明确要求时不要修改产品代码。

## 工具

| 工具 | 用途 |
|---|---|
| `qa_device_status` | 列出在线 Android 设备、iOS 模拟器与占用状态 |
| `qa_run_suite` | 执行一组验证步骤，返回结论、逐步骤明细与截图路径 |

`qa_run_suite` 的关键参数：

- `platform`：`android` / `ios` / `web`
- `target`：Android 包名、iOS Bundle ID 或网页 URL。省略时在当前屏幕继续操作，适合验证已经打开的应用；网页验证必填
- `deviceSerial`：Android 设备序列号，不传则用首个在线设备
- `steps`：字符串数组，按顺序执行

## 步骤写法

- 纯文本 = 操作步骤，例如 `点击底部「我的」标签`
- `断言: ...` = 只判断不改动，例如 `断言: 页面显示头像与昵称`
- `等待: ...` = 轮询等待条件成立，例如 `等待: 列表加载完成`

先操作后断言。一条步骤只描述一件事，避免「点击登录并检查是否成功」这类混合描述。

## 规则

- 同一次验证只占用一台设备；需要跨设备对比时分成多次执行。
- 任一步失败不会中断后续步骤：这是为了留全证据，不要因此认为用例设计失败。
- 失败原因来自 AI 视觉判断，可能误判。连续两次同一断言失败且截图明显满足条件时，改写断言或告知用户，不要无限重试。
- 设备被自动化任务占用时，工具会排队等待。等待期间如实告知用户，不要切换到其他设备掩盖问题。
- 汇报必须带证据：结论、失败步骤、截图路径，缺一不可。
